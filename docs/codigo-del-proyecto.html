Qué es

Un sistema de registro académico sobre Oracle Database: estudiantes, materias, profesores y matrículas, con administración de almacenamiento, usuarios, backups y auditoría, y una aplicación web para operarlo.

Parte del taller del Caso 4, cuyo script de tablas y datos se usa sin cambios. Sobre esa base se agregó una tabla de estudiantes, la capa de administración de la base y la interfaz web.

Arquitectura

El navegador nunca habla con Oracle. Habla con la API de Next.js, y cada petición se ejecuta con el usuario de Oracle de quien inició sesión. Por eso los permisos y la auditoría los aplica la base, no la aplicación.

Cómo se ve una petición

  1. La persona inicia sesión con su usuario de Oracle. crea un pool autenticado y lo guarda en memoria del servidor; la contraseña no se guarda.
  2. Cada ruta de la API toma ese pool con y ejecuta el SQL con variables enlazadas.
  3. Si Oracle rechaza algo, convierte el código ORA en un mensaje claro según la restricción que falló.

Decisiones que conviene explicar

  • El administrador no tiene CREATE USER ni ALTER USER. Solo puede ejecutar , que valida el nombre (U_*), el rol y la contraseña. Por eso no puede tocar a SYSTEM ni a otros esquemas.
  • UNIV_SEC no tiene contraseña (NO AUTHENTICATION): nadie puede iniciar sesión con la cuenta dueña de la bitácora.
  • Perfil PERF_UNIV_USUARIOS: bloqueo tras 5 intentos fallidos durante una hora, contraseñas de 180 días, sin reutilizar las 3 últimas, y la función .
  • La web solo escucha en el mismo computador (127.0.0.1), rechaza peticiones de otros orígenes y usa una cookie HttpOnly y SameSite=Strict.

Separar índices de datos permite recuperarlos por aparte. Durante las pruebas apareció un efecto de esto: con el datafile de datos perdido, SELECT COUNT(*) seguía funcionando porque Oracle lo resolvía con el índice. Por eso la demo de recuperación usa COUNT(semestre), que sí obliga a leer la tabla.

RMAN en caliente requiere ARCHIVELOG, que activa .

Hallazgo de las pruebas: impdp con TABLE_EXISTS_ACTION=REPLACE recrea las tablas y deja la política de auditoría de datos activa pero vacía. El script de import la vuelve a crear y comprueba que tenga sus 12 acciones.

Auditoría

Hay dos registros que se complementan:

  • Bitácora propia (UNIV_SEC.BITACORA): un trigger por tabla guarda quién cambió qué fila, desde dónde y sus valores antes y después en JSON. Otro trigger impide modificarla o borrarla.
  • Auditoría unificada de Oracle: inicios de sesión exitosos y fallidos, administración de cuentas y tablespaces, y cambios en las cuatro tablas.

Guion de la demo

  1. Reportes: las 4 consultas del taller con enunciado, SQL y resultado.
  2. Registro completo como U_OPERADOR: registrar un estudiante, una materia y un profesor; asignarle la materia (desde Materias del profesor o Profesores de la materia); y matricular al estudiante. Luego mostrarlo en SQL Developer.
  3. Permisos: como U_CONSULTA, ejecutar DELETE FROM matriculas en la consola. Oracle lo rechaza.
  4. Integridad: crear un curso con 9 créditos, borrar la materia 101 y registrar un correo repetido.
  5. Auditoría: como U_AUDITOR, ver los cambios del paso 2 con usuario y valores.
  6. Usuarios: como U_ADMIN, crear, cambiar de rol y bloquear un usuario.
  7. Almacenamiento: tablespaces y dónde está cada objeto.
  8. Recuperación: ejecutar backup/demo_2_perdida_datafile.sh en vivo.
